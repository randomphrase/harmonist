{# One page of the Library grid — search, filters, tiles, pager — as a whole. It used to be an accumulator: the first page opened #library-grid and every later page appended tiles plus a fresh Load-more button. That made the grid's position unaddressable (it only existed as DOM you'd built by clicking), so a trip to an album page and back dumped you on the newest 30 (#139). Each page is now a complete, self-describing render that replaces #library-rows. The root element below carries the refresh wiring, so each render re-requests the page it is actually showing. Putting that on the #library-rows container instead needs the page in an `hx-vals`, and hx-vals is INHERITED: every pager link inside would then send its own `?page=2` plus the container's `?page=1`, and the last value wins — which silently pinned the grid to page 1. Here there is no inherited value to collide with, and a refresh mid-browse (every `tasks-changed`) keeps you on your page. It also carries the dataset that says what this render *is*: which slice is on screen (`data-page`, `data-limit`) and how big the whole Library is (`data-total-done` — unfiltered and unsearched, #140's constraint, since a paginated grid cannot be counted by its rendered rows). The browser tests read it to tell an in-place swap from a page load. It used to hang off a `LIBRARY · N done` heading here, which repeated the tab label and count directly above it and called every terminal album "done" while the chips below offered to filter the Incomplete ones — so the heading went and the dataset stayed (#217). #} {% from 'macros.html' import library_query %}
{# Search (#180). The filters below find albums that are *wrong*; this finds the album you have in mind, which at library scale is the more common errand and the one paging cannot help with. `hx-preserve` on the input, and it is load-bearing: this whole partial is replaced on every `tasks-changed` and `library-refresh`, so without it a scan finishing while someone types eats what they had typed, mid-word. Preserving the node carries the value and the caret position across the swap — htmx moves the live node into the new content rather than rebuilding it. Focus itself is still dropped (the node is detached and reattached), so a background refresh mid-typing costs one click to resume; it no longer costs the query. The form could have gone OUTSIDE #library-rows instead, which would keep focus too — but then the hidden `filter` below would never re-render, and a chip click would leave the form submitting searches scoped to the filter *before* the one on screen. A rare lost focus beats a silently wrong search. The cost of preserving is that the server can no longer change what is in the box, which is why the two controls that clear a search are plain links with no `hx-get` — a full navigation, which rebuilds the DOM and so genuinely empties it. (A clamped over-length query is the one case the box can disagree with what was searched; 100 characters in, it is not a disagreement anyone will notice.) `submit` is named in the trigger list, not assumed: naming `search` alone would REPLACE the form's default rather than extend it, and every Enter would escape htmx into a native navigation (#144's bug, `web-ui` rule 2b). `search` is there for the native clear button `type="search"` gives us in Chrome and Safari — it fires that event, so clearing the box re-runs the query with nothing in it. No `limit` field: the page size lives in a cookie the route falls back to, kept in step with every explicit `?limit=`, so sending it here would be a second copy of the same fact, free to disagree with the first. `hx-headers` rather than a hidden input, because this is a message to the server and not part of the view: it asks for an `HX-Push-Url` naming the resolved URL, which the form cannot spell itself (it knows neither the size nor the page the query will land on). A hidden field would strand the marker in the address bar on the no-JS path, which is exactly the wart `?anchor=` leaves. #} {% if total_done %}
