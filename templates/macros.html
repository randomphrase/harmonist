ONE definition because the Library page renders this string in twenty places — the container's refresh wiring, the page-size form, the search-widening link, every filter chip and both pager arrows (as an href AND an hx-push-url each), and the tile links — and a parameter dropped from any one of them is a control that silently throws away part of the view. That is not hypothetical: the set has grown from `page` to `page + limit` to `page + limit + filter` to this in four issues (#139, #144, #174, #180). Because Jinja renders a missing argument as an empty Undefined rather than raising, a call site left behind at three arguments would drop `q` on that one control and look completely fine. `make template-lint` therefore requires all four at every call site — a mechanical rule for a mechanical hazard. `filter` is omitted when falsy so All keeps the short URL — absence IS All, so there is no `filter=all` to spell. The slug is interpolated raw; that is safe because it reaches here only via `_library_filter`, which checks it against the known set. `q` is free text and gets no such guarantee, so it is urlencoded: a bare `&` or `#` in a query would end the URL early and silently drop whatever came after it. `page` is omitted when falsy too, which is how the filter and search controls ask for one: asking a new question starts at the first page of the answer, and the route's default is 1. Passing the current page across would request page 7 of a 3-album result. #} {% macro library_query(page, limit, filter, q) -%} {% if page %}page={{ page }}&{% endif %}limit={{ limit }}{% if filter %}&filter={{ filter }}{% endif %}{% if q %}&q={{ q | urlencode }}{% endif %} {%- endmacro %} {# How far an update reaches, as one chip (#366). `owned.Significance` ranks four levels by how much of the album they call into question — cosmetic, enrichment, structure, identity — with artwork a fifth on its own axis rather than a rank among them. The same action blocks serve two hosts. In the inbox a card mutates an album and lets the inbox re-render around it, which is why nearly all of them are `hx-swap="none"` and say nothing about where the answer goes. On the album page there is no inbox to re-render, and every one of these actions changes what the page is describing: a confirm tags the album and sends it to the Library, a reject clears the very suggestion being shown, a surrender moves it out of the inbox entirely. So the page reloads itself and lets the server render the album's new state, rather than patching regions from a response shaped for somewhere else. It reloads rather than navigating away because the album still exists and is still what the reader came for — and `_find_album` resolves the id in the URL even after tagging has replaced a temp uid with the release MBID, which is exactly what a confirm does. Gated on `event.detail.successful`: reloading over a failure would throw away the flash that says what went wrong. `hx-on::after-request`, never `onclick` — an inline onclick beside hx-* attributes runs first and can detach the element before htmx fires at all (web-ui rule 2a, and `make template-lint` enforces it). #} {% macro reload_on_success(active) -%} {% if active %}hx-on::after-request="if (event.detail.successful) window.location.reload()"{% endif %} {%- endmacro %} {# The same, for a control whose response is sometimes a list to READ rather than a change to absorb (#150).
